# ADR-073 — a committed artifact nothing can write

**Status:** accepted (2026-08-22) · **Release**: v0.115.0

## Context

ADR-068 measured coverage over `src/` for the first time and found 93
functions with zero executed statements. Triaged, six were genuinely dead, and
it named two of those as more than dead weight. This is one of them:

> `lanes/calibrate_perf.py:record_calibration` — the **only** writer anywhere
> in the repo of `benchmarks/perf_seeded/calibration.yaml`. […] The narrower
> true fact: the committed artifact **cannot be regenerated by any code
> path**, only hand-edited.

Assembled, the arrangement was:

* `benchmarks/perf_seeded/calibration.yaml` is committed. It was added by
  `cbbd421`, *"feat(lanes): v0.24.0 — … the perf lane is CALIBRATED"*.
* `lane_status()` reads it and returns `CALIBRATED (loopback, low parity,
  relative detection, 2026-07-26)`.
* `run_perf_calibration()` — tested, at `test_lane_runners.py:76`.
* `record_calibration()` — the only writer. **No caller.**

So the lane's advertised status rested on a file the codebase could read and
could not produce. Nothing was wrong with the reading; it was taken honestly
in July. What was missing was the ability to take it again, and any way for a
reader to see how old it was.

And it was old in the way that matters. `lane_status()` reported the *date*,
2026-07-26. It did not report that the reading came from **v0.24.0** while the
build asking the question was **v0.114.0** — ninety releases later. This is
exactly ADR-054's finding at a second reader: `avs cadence` printed `ok (4d)`
over a bench result that was nine releases old, because days are a proxy that
breaks precisely when releases outpace measurement.

## Decision

**Wire the writer, and make every reading name the build that took it.**

1. **`avs perf-calibrate`** runs the calibration and records it. Free and
   local — a loopback HTTP server over a seeded sqlite database, no provider,
   no network, no spend. `--dry-run` measures and prints without writing.
2. **`record_calibration` stamps `avs_version` on every record**, not only on
   ones that turn out to be stale. A field that appears exactly when something
   is wrong is a field nobody looks for (ADR-056).
3. **`lane_status()` names the build**, and names the current one when they
   differ:

   ```
   CALIBRATED (loopback, low parity, relative detection, 2026-07-26 on
   v0.24.0, current build v0.114.0)
   ```

4. **The committed reading is backfilled** with `avs_version: 0.24.0`,
   recovered from the commit that added it — not guessed. The file says so in
   a comment, because a hand-written key in a machine-written file should not
   be indistinguishable from a machine-written one. It is an insertion: no
   recorded value was altered.

### Staleness is described, never a downgrade

`lane_status()` does **not** demote a reading to `PROVISIONAL` because the
build moved. Nothing in this module knows whether the perf lane's behaviour
actually changed between two builds, so a version-triggered downgrade would be
a guess wearing a verdict's clothes — and it would make `avs perf-calibrate`
mandatory on every release for a lane nobody touched. The 80% catch-rate bar
that decides `CALIBRATED` vs `PROVISIONAL` is untouched.

This is the same posture ADR-059 landed on: close the gap by *describing*, not
by refusing.

### The measurement is cheap and still a measurement

`avs perf-calibrate` costs nothing, which makes it tempting to run on a
schedule. It should not be. The reading it writes **replaces** the one on
disk, and it is environment-dependent by its own admission
(`environment: loopback`, `parity: low`) — a run on different hardware is a
*different reading*, not a refresh of the old one. Run it deliberately, the
way a bench is run deliberately. `--dry-run` exists so that looking is not the
same act as replacing.

For that reason this change does **not** regenerate the committed file. The
gap was that it *could not* be regenerated; it can now, and the decision to
spend a new reading stays a human one.

## Mechanism

`tests/test_the_calibration_can_be_regenerated.py`, 9 tests. The command is
entered through `CliRunner` rather than by calling the function — ADR-068's own
finding was that the defect that started this lineage (`bench-criterion`'s
`NameError`) lived in the CLI wrapper, ten lines below where `--help` stops
looking.

⚠ **No test writes the real `CALIBRATION_FILE`.** It is a committed
measurement, and a test that overwrote it would replace a recorded reading
with one taken on CI hardware and report that as a pass — ADR-056's shape
exactly. Every test touching the write path redirects the module constant to a
tmp path first.

Pinned in both directions: an unstamped file reads as *"an unrecorded build"*
and never as the current one, and a stale stamp still reports `CALIBRATED`.

## What stays out

**A staleness threshold.** ADR-054 declined one for `avs cadence` and the
reason holds here: a number that triggers a warning is a number people learn
to dismiss, and there is no honest constant for "how many releases before a
loopback perf reading stops being true."

**Running it in CI.** The reading is hardware-dependent and CI hardware is not
the hardware anyone cares about. A green CI run writing a calibration would be
the cheap-substitute-corrupts-the-ledger defect (ADR-053/056/066) for a
fourth time.

PC-1 2487 → **2501**. Version 0.114.0 → **0.115.0**.
